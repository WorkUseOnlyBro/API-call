# API to SQL Database Import Script

This script pulls data from an external API and inserts it into a SQL Server database. It is designed to run automatically on a job scheduler (twice daily) and handles pagination, error logging, and optional email reports.

---

## How It Works (High Level)

1. The script figures out what date range to pull data for.
2. It connects to the API and requests data one "page" at a time (100 records per page by default).
3. Each page of data gets inserted into a SQL Server table, row by row.
4. After all pages are processed, it logs a summary and optionally sends an email report.
5. It records the current time in the `API_Last_Run` database table so the next run knows where to pick up.

---

## Configuration (Top of the Script)

All settings live at the top of the script file. Here is what each section does:

### API Configuration

```python
api_url = "URL"
password = "password"
arc_id = "id"
hash_value = "hash"
```

These are the credentials and endpoint for the API. The `password`, `arc_id`, and `hash_value` get sent as HTTP headers with every request.

### Date Range Configuration

```python
date_mode = "since_last_run"
```

This controls what time range the script asks the API for. There are three options:

| Mode | What It Does |
|------|-------------|
| `"since_last_run"` | Looks up the last time the script ran successfully (from the `API_Last_Run` table in the database) and only pulls data from that time until now. This is the recommended mode for scheduled runs. |
| `"previous_day"` | Pulls all data from yesterday. Uses date-only format (`YYYY-MM-DD`). |
| `"manual"` | Uses the `manual_start_date` and `manual_end_date` values you set below it. Good for backfills or one-off pulls. |

**First run behavior:** If `since_last_run` is selected but there is no previous run recorded in the database yet, it falls back to pulling the previous day's data automatically.

```python
manual_start_date = "2026-01-28"
manual_end_date = "2026-01-29"
```

These only matter if `date_mode` is set to `"manual"`. Set them to whatever date range you need.

### Email Configuration

```python
send_email_report = False
```

Set this to `True` to send an email summary after each run. You will also need to fill in the SMTP server settings, from/to addresses, and subject line below it.

### Pagination Settings

```python
page_size = 100
start_page = 1
max_records = 10000
```

- **page_size**: How many records to request from the API per page. The API returns data in chunks -- this controls the chunk size.
- **start_page**: Which page number to start from (almost always leave this at 1).
- **max_records**: A safety cap. The script will stop pulling after this many records even if more data is available. Set to `None` to disable the limit entirely.

### SQL Server Configuration

```python
sql_server = "sql ip"
sql_database = "DBPlaceHolder"
sql_table = "SQLTablePlaceHolder"
sql_username = "username"
sql_password = "password"
```

Connection details for the SQL Server database where data gets inserted.

### Column Mapping

```python
column_mapping = {

}
```

If the API returns field names that don't match your SQL table's column names, you can map them here. For example:

```python
column_mapping = {
    'apiFieldName': 'SqlColumnName',
    'firstName': 'first_name',
}
```

If left empty, the script uses the API field names as-is (meaning your SQL columns need to match the API field names exactly).

## Functions Explained

### `get_last_run_time()`

Opens a separate connection to the database and runs:

```sql
SELECT MAX(last_run_time) FROM API_Last_Run
```

This gets the most recent timestamp from the run history table. Returns the timestamp as a string like `2026-04-07T14:30:00`, or `None` if the table is empty (first run).

### `save_run_time(conn, cursor)`

After a successful run, this inserts the current time into the `API_Last_Run` table:

```sql
INSERT INTO API_Last_Run (last_run_time) VALUES ('2026-04-07T14:30:00')
```

This builds up a history of every run. The most recent entry is what `get_last_run_time()` reads on the next run.

### `get_date_range()`

Decides what start and end dates to use based on the `date_mode` setting. Returns two strings that get plugged into the API request URL as `startDate` and `endDate`.

- **`"since_last_run"`**: Calls `get_last_run_time()` for the start, uses current time for the end. Both use full timestamp format (`YYYY-MM-DDTHH:MM:SS`).
- **`"previous_day"`**: Calculates yesterday's date. Uses date-only format (`YYYY-MM-DD`).
- **`"manual"`**: Just passes through whatever you set in `manual_start_date` and `manual_end_date`.

### `fetch_page(page_number)`

Makes a single API call to get one page of data. Here is what it does step by step:

1. Calls `get_date_range()` to get the start and end dates.
2. Builds the request URL with the dates, page size, and page number as query parameters.
3. Sends a POST request with the authentication headers.
4. If the response is successful and contains data, it returns the list of records.
5. It also returns a True/False flag for whether there are probably more pages (it checks if the number of records returned equals the page size -- if so, there is likely another page).

### `insert_page_to_database(conn, cursor, data_entries, page_number)`

Takes a list of records (one page worth) and inserts them into the SQL table one row at a time:

1. Reads the field names from the first record.
2. Applies the column mapping (if configured) to translate API field names to SQL column names.
3. Builds an `INSERT INTO ... VALUES (...)` SQL statement.
4. Loops through each record and executes the insert. If a single row fails, it logs the error and moves on to the next row (it does not stop the whole batch).
5. Commits the page to the database and returns the count of successes and errors.

### `send_report_email(...)`

Builds and sends a plain-text email summary of the run. Only runs if `send_email_report` is set to `True`. The email includes:

- Start/end time and duration
- Date range queried
- Number of records inserted and errors
- A warning if the max record limit was hit
- A list of any error messages

### `main()`

This is the entry point that ties everything together. Here is the flow:

1. Gets the date range for this run.
2. Logs the run configuration (dates, page size, target database, etc.).
3. Connects to SQL Server.
4. Enters a loop that:
   - Fetches a page of data from the API.
   - Inserts that page into the database.
   - Checks if there are more pages or if the max record limit has been reached.
   - Moves to the next page if there is more data.
5. After the loop, saves the current timestamp to `API_Last_Run` (only if at least one record was inserted successfully).
6. Closes the database connection.
7. Logs a final summary with totals.
8. Sends the email report (if enabled).

If the database connection fails or any major error occurs, it catches the error, logs it, and still produces the summary/email so you know something went wrong.

## Database Requirements

### Main Data Table

Your SQL table (set in `sql_table`) needs columns that match either the API field names or your column mapping. The script does not create this table -- it must already exist.

### Run History Table

The script expects this table to exist for tracking run times:

```sql
CREATE TABLE API_Last_Run (
    id INT IDENTITY(1,1) PRIMARY KEY,
    last_run_time DATETIME2
);
```

- **id**: Auto-incrementing row number. Each run adds a new row so you have a full history.
- **last_run_time**: The timestamp of when the script ran.

---

## Running in a Container

This script is designed to run inside a Docker container. Since the run history is stored in the database (not a local file), there is nothing on the container's filesystem that needs to persist between runs. The container can be rebuilt or restarted freely without losing track of the last run time.

---

## Logging

The script logs everything to the console (stdout). Log levels used:

- **INFO**: Normal operation messages (connecting, fetching pages, inserting rows, summaries).
- **DEBUG**: Detailed technical info (full URLs, SQL statements, row-level details). Useful for troubleshooting.
- **WARNING**: Non-fatal issues (max record limit reached, no previous run found).
- **ERROR**: Failures (database connection errors, failed row inserts, API errors).

Since this runs in a container, these logs will show up in your container's log output (e.g., `docker logs`).

## Common Tasks

### Backfill data for a specific date range

1. Set `date_mode = "manual"` at the top of the script.
2. Set `manual_start_date` and `manual_end_date` to the range you need.
3. Run the script.
4. Set `date_mode` back to `"since_last_run"` when done.

### Check when the script last ran

Query the database:

```sql
SELECT TOP 10 * FROM API_Last_Run ORDER BY last_run_time DESC;
```

### Increase or remove the record limit

Change `max_records` at the top of the script. Set it to `None` to remove the limit entirely (be cautious -- this could pull a lot of data).
